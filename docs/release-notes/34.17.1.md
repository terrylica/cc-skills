## [34.17.1](https://github.com/terrylica/cc-skills/compare/v34.17.0...v34.17.1) (2026-11-15)

This patch fixes two bugs in FloatingClock's new power rail, both found within hours of 34.17.0. With the rail on, the app crashed whenever a Bluetooth device connected, and at every launch while one was connected, so it could not be opened at all. IOBluetooth delivers its connect notifications on its own thread, and the rail's handler went straight into window code that AppKit allows only on the main thread. Registering for those notifications also reports every device already connected, which is why launch was affected. The handlers now move to the main thread before doing anything. The second bug showed AirPods twice on a Mac with two pairings of the same name: battery readings were matched to devices by name alone. Readings that IOBluetooth takes from a connected device are now tied to that device's address.

### Summary

- **floating-clock, crash** ([#97](https://github.com/terrylica/cc-skills/pull/97), closes [#96](https://github.com/terrylica/cc-skills/issues/96)):
  - **Trigger:** `EXC_BREAKPOINT` "Must only be used from the main thread", from an IOBluetooth connect notification reaching `-[NSWindow setFrame:]`.
  - **Fix:** both connect handlers hop to the main queue, and `refreshNow` re-dispatches itself if called from any other thread.
  - **Verified:** with AirPods connected and the rail on, the app relaunched twice without a crash. The 34.17.0 build crashed at every launch in that state.
- **floating-clock, duplicate device:**
  - **Matching:** IOBluetooth's readings attach by device address. Accessory parts match by name with the owner prefix ignored, preferring the connected pairing.
  - **Filling:** a device with exact readings takes only parts it lacks (the case), never a combined figure beside left and right ones.
- **Tests:** a case that replays the live two-pairing data. It fails on the old merge and passes now; 156 tests pass.
- **Placeholders:** the model's examples use a neutral owner name.

## [34.8.1](https://github.com/terrylica/cc-skills/compare/v34.8.0...v34.8.1) (2026-10-27)

Rolling 34.8.0 out to other Macs exposed two things that could not be seen on the machine it was built on. Run over ssh, the new tab tool did not fail with the documented -600: Chrome's `running()` answered, then `windows()` hung, and macOS put an Automation prompt ("sshd-keygen-wrapper wants to control Google Chrome") on the screen of whoever was sitting at that Mac. A tool that pops a permission dialog on someone else's screen is worse than one that fails, so the tab tool and `rotate-token` now refuse in an ssh session before any Apple event is sent, and a hung osascript is named instead of reported as an empty error. Separately, the hook's regression test failed on every stock Mac because macOS ships bash 3.2, which brace-expands JSON written inside a quoted command substitution; the hook itself was fine, and the test now builds its JSON with jq.

### Summary

- **chrome-profiles:** `chrome-tabs.ts` refuses when `SSH_CONNECTION`, `SSH_CLIENT` or `SSH_TTY` is set (`CHROME_TABS_ALLOW_SSH=1` overrides for a Mac you are sitting at), so no Automation prompt appears on a remote screen.
- **chrome-profiles:** a 15 s osascript timeout is reported as "not the desktop session, or an Automation prompt is waiting", exit 4, instead of `osascript failed:` with nothing after it.
- **chrome-profiles:** `rotate-token` applies the same ssh guard, checking the same three variables.
- **chrome-profiles:** the browser-MCP reminder hook test builds JSON with jq and passes 12/12 under stock `/bin/bash` 3.2 as well as bash 5.
- doctrine.md replaces the inferred -600 explanation with the measured ssh behaviour; SKILL.md says never to answer such a prompt with Allow.

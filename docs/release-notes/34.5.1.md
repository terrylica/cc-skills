## [34.5.1](https://github.com/terrylica/cc-skills/compare/v34.5.0...v34.5.1) (2026-10-24)

The floating-terminal skill shipped in 34.5.0 could not find Orca on Linux at all, which a live check on a Linux host found within the hour. Orca 1.4.224 installs its command-line tool on Linux as `orca-ide`, under `/opt/Orca/resources/bin/` and linked into `PATH`, because `/usr/bin/orca` there is the GNOME screen reader. The shared finder only ever looked for a binary called `orca`, so on every Linux desktop `orca-float` reported "Orca IDE CLI not found" even with Orca running. This patch teaches the finder the Linux name and its install locations. It also makes a refused terminal report Orca's own reason, for example that no Orca app is running for the current user, instead of a Python traceback and a guess about settings.

### Summary

- **orca-tools:** the shared Orca CLI finder now also looks for `orca-ide`: in `$ORCA_CLI_BIN_DIR`, on `PATH`, in `~/.local/bin` and in `/opt/Orca/resources/bin`. It still checks every candidate's help text, so the screen reader is never mistaken for Orca.
- **orca-tools:** when `orca terminal create` fails, `orca-float` prints Orca's own error code and message (such as `runtime_unavailable`) to stderr and exits 1, with no traceback.
- **orca-tools:** the skill now says that Orca's CLI reaches the Orca app of the same user only, so over SSH as another account `doctor` reports that reason.
- Two new tests (14 in total): the Linux `orca-ide` name found on `PATH` without `ORCA_CLI`, and Orca's refusal surfaced cleanly.
- Verified live: `doctor` on Linux found `/usr/bin/orca-ide` and reported Orca's reason, and `doctor` on macOS was unchanged (probe landed in the floating terminal).

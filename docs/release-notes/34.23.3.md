## Narrative

This patch release makes the orca-tools worktree-spinoff skill reliable when it starts work on another computer. Spinning a task off onto a paired Orca runtime pushes the handoff to a staging branch, and the runtime's own clone must have fetched that branch before Orca can base the new worktree on it. The script checked for it once, the instant after pushing, so it lost that race and stopped with "the target runtime's clone has no ref", cleaning up after itself: twice in a row on 2026-11-23, while the remote clone was fetching every three seconds. It now waits for the clone for up to a minute before giving up, so a spin-off to another machine goes through on the first try instead of needing a manual fetch and a retry.

## Fixed

- **Waits for the remote clone:** after pushing the staged handoff, `orca-spinoff` asks the target runtime for the branch (`orca repo search-refs`) every 3 seconds for up to `SPINOFF_REF_WAIT` seconds (default 60), instead of checking once ([#133](https://github.com/terrylica/cc-skills/pull/133)).
- **Clearer failure:** when the branch still has not arrived, the error says how long it waited and to run `git fetch` in that clone, then retry.
- **Same cleanup:** on a failure the staging branch and the temporary worktree are still removed, so a retry starts clean.
- **Local and host targets unchanged:** the wait applies only to a paired runtime reached with `--environment` or `--pairing-code`; spin-offs on this machine or on a project host behave as before.

## Documentation

- **New pitfall in the skill:** "A paired runtime's clone fetches after the push, not at it", with what was measured and what to do if a clone never fetches by itself.
- **Proved live:** with the change, the third attempt created the worktree on the remote runtime, and its agent started there.

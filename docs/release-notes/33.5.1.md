## v33.5.1 — 2026-10-04

v33.5.1 makes two guards work again after the operator's repositories moved from personal accounts into GitHub organizations under `~/gh/<org>/`. Both guards had been quietly doing nothing there. The gh-tools identity guard is meant to stop a `gh` write going out under the wrong GitHub account. It read the target repository from `git remote get-url`, but in the new layout git rewrites every canonical remote to an account-specific SSH alias, and the guard's pattern never matched that form. So it found no target and allowed every write. The TypeScript drift guard had the same kind of blind spot: it searched the removed `~/own` folder, so it had skipped every repository under `~/gh` since the move.

### Fixed

- **gh-tools identity guard reads the stored remote** (`gh-repo-identity-guard.mjs`): it uses `git config remote.origin.url`, the canonical form that is never rewritten, and accepts alias hosts too, so the target repository is found under `~/gh/<org>/` again.
- **Account resolved from the folder** (`gh-repo-identity-guard.mjs`): the account comes from `git config gh.account`, set per organization by the per-account git config, before falling back to the SSH alias of the old layout.
- **Own-organization fast path** (`gh-repo-identity-guard.mjs`): a write to the repository's own organization is allowed without an API call when the folder chose the account and no `GH_TOKEN` is exported. With a `GH_TOKEN` exported, that token's push access is still checked, because a stray exported token is exactly the wrong-account incident the hook exists for.
- **TypeScript drift guard searches `~/gh`** (`1fa92c9b`): its default roots are `~/eon`, `~/gh` and `~/vj`, replacing the removed `~/own`.

### Verified

- Run under bun against both the old and the new hook: a write to the repository's own organization is now recognised, where the old hook allowed it only because it found no target.
- A cptbc token closing an issue on a public vjspc repository is denied by both versions.
- The old alias layout under `~/vj/collab` still allows writes.
- Unchanged by design: a private repository the token cannot read still fails open.

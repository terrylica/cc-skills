**2026-09-05**: `plugins/itp-hooks/hooks/lib/op-token-injector.ts` wrote the 1Password service-account token to disk in plaintext on **every** `op` call against the Claude Automation vault, for about seven months, **by design and working exactly as written**. The hook existed to avoid Touch-ID prompts and did it by rewriting the Bash command to `OP_SERVICE_ACCOUNT_TOKEN='<literal>' <command>` — and Claude Code records the rewritten tool input in the session transcript AND in the background-task output file. Measured 2026-09-05: the token appears verbatim in **91 files — 58 under `~/.claude/projects`, 33 under `/private/tmp/claude-501`**. Fixed by emitting `"$(cat '<path>')"` instead, so the path goes into the command and the shell resolves it at execution time; fail-open semantics are unchanged because the file is still read for the missing/unreadable/empty checks, and only the value is kept out of the string. **Three things generalise.** (1) **Rotation ordering:** the injector had to be fixed BEFORE rotating, or the new token would be written to disk on the first `op` call — rotation without the fix is theatre. (2) **`/private/tmp/claude-501` is a store nobody counts.** It holds every backgrounded command's and every subagent's output, it accumulates across sessions and days (measured: 433 files, 1.3 GB, four days), no retention policy covers it, and its owner-only protection is exactly **one directory deep** — `drwx------` at the root, `drwxr-xr-x` and `-rw-r--r--` beneath, so any `tar`/`rsync`/backup preserving modes exposes it with no further mistake. Audit it alongside `~/.claude/projects`, and note the latter is itself three stores (session JSONL, `**/tool-results/*.txt` for outputs over ~40 KB, and `**/subagents/workflows/**/*.jsonl`). (3) **A credential audit must prove a hit without rendering it** — `grep -l` and `grep -c` are the only two verbs it may use, and `grep -F -f <file>` keeps the value out of argv and the process table. The investigator writing this leaked a (already-cancelled) key into their own transcript minutes after stating that rule, via `${VAR:-<unset>}` — which reads as a null check and is an **interpolation**. Name the safe idiom, not the intent: `[[ -n ${VAR:-} ]] && echo SET || echo unset`. **And delete the credential file LAST** — the audit reads its search pattern from that file, so destroying it first destroys the only means of locating its own copies, and freezes whatever count you had as the permanent ceiling of what you can know.

**2026-09-05**: Before any sweep, for each site your regex matched, **find where that site's reason is recorded — and treat "nowhere" as a finding rather than as permission.** Three near-misses in one day, each a value that differs from its neighbours for a real reason, and in two of the three a test was the only thing between the sweep and a regression. They are not one class, and the distinction is what makes the rule worth its cost. **ACTIVELY MISLEADING** is the dangerous grade: crucible's "18 principles across 4 skills" sits directly above a table listing **5** items, so the file appears to contradict itself on its face — a reader checking the surrounding lines concludes "obvious typo" and is wrong, and the more diligently they verify against what is on screen the more confidently wrong they get, because the reason (the 18 principles genuinely span 4 skills; the 5th is a router carrying none) is unrecoverable from the file. That inverts the usual heuristic: proximity is normally evidence, and here it is the trap, so "I checked the neighbouring lines" actively makes it worse. **UNEXPLAINED** is the milder grade: `itp/ 4-phase workflow` (CLAUDE.md:97, README.md:30/473/542) is correct and nothing local argues against it — it is simply not explained, and it will match any `[0-9]+[- ]phase` regex written for the _release_ pipeline, which is a different thing entirely. The third, `tasks/release/full`, is the case where the reason IS recorded and findable: `full:36-40` explains that the `#MISE depends=["release:preflight"]` declaration was deliberately removed so preflight runs inside the orchestrator body where iter-139's timing wrapper can measure it, and `test-iter137…:253` asserts its absence. Restoring it there "for consistency" would silently destroy the phase-1 wall-clock that iter-74 through iter-138 were built on — so the same declaration is correct on two sibling tasks and actively wrong on a third, with a test pinning the third. Corollary for surveys: when a number comes from a positional field, quote the field's header or the code that parses it, not just the count — a miscount is caught by recounting, and a misread column is not, because recounting reproduces the same number with more confidence.

**2026-09-05**: When a mechanism is superseded, delete every copy of it — a migration that fixes the shared implementation and leaves the per-plugin clones behind ships a loaded gun with the safety off. `scripts/sync-hooks-to-settings.sh` stopped injecting hooks into `~/.claude/settings.json` in v20.2.3 and became a **pruner**, because Claude Code auto-loads each plugin's `hooks/hooks.json` and the second registration made every hook fire twice per event (its header records the observation: the same script listed twice in the runtime's "Ran N stop hooks" display). Five per-plugin `scripts/manage-hooks.sh` generators doing exactly the same injection survived that migration untouched, each fronted by a user-invocable `tether` skill. Audited one by one (issue #127): `itp` → `posttooluse-reminder`, `dotfiles-tools` → `chezmoi-sync-reminder.sh`, `gh-tools` → `webfetch-github-guard.sh` and `productivity-tools` → `calendar-reminder-sync.ts` are **all four** already registered in their own plugin's `hooks.json`, so all four were retired (generator + skill + every doc that told a user to run it). Only `statusline-tools` survives, and for a reason that is the whole test: its `lychee-stop-hook.sh` is **deliberately absent** from `hooks.json`, making the injection the sole registration rather than a duplicate. Three things this surfaced that a "just repair the path" fix would have buried. (1) The `itp` installer had been **inert since a rename** — it verified `posttooluse-reminder.sh` with `-x` and the file became `.ts`, so `do_install` died on line 137 every time and nobody noticed for months, because nothing tested the generator and the validator only parsed the jq literals further down the file. A loud failure nobody ever triggers is indistinguishable from working code. (2) Its second entry, `pretooluse-fake-data-guard.mjs`, is absent from `hooks.json` **because it was deliberately pulled** in `e6c665a9` for blocking legitimate writes — so repairing the installer would have resurrected a guard that had been switched off on purpose. "Absent from hooks.json" is not one condition: it can mean opt-in-by-design (keep the installer) or disabled-on-purpose (never re-inject), and the two look identical from the generator. (3) `productivity-tools`' README advertised its hook as "opt-in, not auto-enabled" while `hooks.json` shipped it enabled — documentation describing the retired mechanism rather than the live one. **Rule: when you convert a shared installer into a no-op, grep for its clones in the same change** (`ls plugins/*/scripts/<name>` costs one command), and make each survivor state in its own header why it is exempt.

**2026-09-05**: The 2026-09-02 `cp -f` truncation race is **still live on a second shared file** — the fix moved, the bug did not. Iter-187 made every write to `docs/marketplace-escape-hatch-marker-reference.md` atomic and left the three writes to `plugins/gmail-commander/scripts/bot.ts` in `test-iter115-…` on `cp -f`, which opens the destination `O_TRUNC`. One tight-loop reader watched both files simultaneously across 34 suite runs: **bot.ts observed EMPTY 3,804 times in 174,050,501 stat() reads; the canonical doc 0 times in the same 174,050,501** — a single measurement carrying both its own positive and its own control. The isolated A/B on the primitive is unambiguous: 3,000 restores via `cp -f backup target` produced **80,303 zero-byte observations in 4,774,675 reads**, 3,000 restores via stage-in-the-same-directory + `mv` (rename(2)) produced **0 in 4,894,396**. Fixed by routing all three producer restores through an atomic same-directory rename — mirroring the doc helper that already sat twenty lines above them in the same file, which is the uncomfortable part — and re-measured in the repo afterwards: **0 zero-byte observations in 103,990,056 reads across 7 further suite runs**, against a scaled expectation of roughly 900 had the `cp -f` survived. **Why iter-192 did not already cover this**: iter-192 serialised the two tree-SCANNERS against each other, which is a _different resource_ — it stops iter-111's synthetic marker being seen by iter-115's clean-baseline scan, and does nothing about a THIRD process reading a truncated `bot.ts`. Third readers demonstrably exist outside this suite entirely: `repo:lint` (`scripts/validate-plugins.mjs`) and `repo:test` run CONCURRENTLY with `repo:test-hooks` inside `moon run repo:check`. **Not claimed as the cause of any observed red run** — no reader was caught failing on it — but it is a measured hazard of the same magnitude as the 453-in-6,353,768 that reddened iter-117 in ~18% of parallel runs, and it is now gone. The generalisable form: when you fix a race by making one file's writes atomic, grep for the _primitive_, not for the file — `cp -f` into a shared path is the defect, and it had two homes.

**2026-09-05**: The iter-160 doctor resolved its repo root from the **caller's cwd** (`git rev-parse --show-toplevel`) instead of from its own location, so it could report a perfectly healthy toolkit as broken — and its failure signature was **indistinguishable from the open flake's**. Run from any other git repository the walk-up succeeds, returns the wrong tree, every derived shared-library path misses, and the doctor emits `verdict=TOOLKIT_BROKEN, critical_failed=13`, which is exactly what the iter-160 regression test's C3/C4 report. Measured: **604 consecutive invocations from `~/eon/ccmax-monitor` all TOOLKIT_BROKEN, against 1,480 from inside cc-skills all TOOLKIT_HEALTHY.** How it was found is the actual lesson: **an investigator's own probe tripped it within five minutes of being pointed at the doctor, and for one exchange it read as a reproduction of the flake.** A diagnostic that can blame the tree for the caller's working directory does not merely fail — it manufactures corroboration for whichever theory you were already holding, which is precisely the trap the 2026-09-02 entry named. Fixed with the iter-176 `${BASH_SOURCE[0]}` pattern the iter-153 advisor already uses (it also removes one `git` fork, harmless to iter-174's A6 whose shim set excludes `git`), plus an iter-181-style fail-fast: a root override that is not a cc-skills checkout now exits **2** — a harness error, deliberately distinct from 1 = toolkit broken — and emits no verdict field at all. Pinned by `test-iter193-…`. **Two of that new test's own assertions were regression-blind on first draft, and only negative-controlling the instrument against `git show HEAD:` caught them**: A2 anchored its `awk` with `^` and scored the pre-fix source 0 — green on the exact defect it exists to catch — because the offending line reads `if ! ITER160_…="$(git rev-parse …)"` with the assignment mid-line; and C2 asserted the absence of the token `TOOLKIT_BROKEN`, which failed against a _correct_ fix because the new harness-error message says in prose that it is not reporting one. **Rule, restated from the other direction to the 2026-09-05 C6 entry below: run every new assertion against the broken input before you believe a green one.**

**2026-09-05**: A second strand of the intermittently-red suite is now **NAMED but still UNRESOLVED**, and the reason it stayed anonymous for five weeks was a formatting detail, not a hard problem. The 2026-09-02 entry below prescribes "loop the suite and tee the actual failing section"; that advice was followed and still lost the name, because of how the runner prints. `tasks/test-marketplace-hook-regression-suite` **did** already re-print a failing-file roster at the end — but those lines read `- <path>`, carrying no word any plausible filter would keep, while the three count lines carried `Test files` / `PASSED` / `FAILED`. So a `| grep -E 'PASSED|FAILED'` (or moon's own truncated log skim) kept **exactly the lines without the name and dropped exactly the lines with it**. The roster was there the whole time; it was unsurvivable, which is operationally identical to absent. Fixed with three redundant carriers rather than one: the failing names and exit codes are appended **to the count line itself** (the line empirically proven to survive), every roster line is prefixed with a `FAILED-TEST-FILE` token, and the whole roster is mirrored to **stderr**, which a stdout-only pipe never touches. Deliberately did **not** reuse the existing `FILE-FAIL`/`FILE-PASS` tokens: the iter-75 parity test and the triage task both `grep -c` those, so re-emitting them would have silently inflated two unrelated tallies — a new signal must not be spelled like an existing counted one. With the carriers in, **1 of 10 `moon run repo:check` runs went red and named itself instantly**: `test-iter160-operator-facing-commits-arc-self-diagnosis-…`, failing C3/C4 because the commits-toolkit doctor reported a CRITICAL check failed. Two measurements narrow it without explaining it: D1, a **second** doctor invocation seconds later **in the same run**, saw all CRITICAL checks pass — so the doctor flaps within a single test — and the doctor run standalone at 12-way self-contention was clean 0/24, so it needs full-suite load, not merely concurrency. **Root cause NOT found; no claim is made.** Note this is the same test family the 2026-08-31 entry already named (`iter160`, `iter166`), consistent with its "plural noun" warning. The carriers then earned themselves twice over within the same session: a later unrelated gate run went red on a **different** member, `test-iter123-unified-lookup-cli-auto-detects-query-shape-…` (exit=1), which the count line named immediately and which passed standalone (exit 0) and green on the next full run — a third distinct member caught on its first occurrence rather than after five weeks of anonymity. That is the actual deliverable here: not a fix, but the end of unidentifiable red runs in this suite. One further trap worth generalising: the red log named the FILE but not the CHECK — the same unidentifiable-failure shape one level down, since C3/C4 printed only an aggregate verdict while holding the full JSON in a variable. Emitting the per-check detail immediately exposed that the emitter had been written against **guessed** schema keys (`status`/`detail`; the real ones are `outcome`/`diagnostic_message`), so it would have shipped printing `outcome=None` for every record and been useless at precisely the moment it was needed. **Rule: an error-path emitter is only exercised when something is already broken, so its assumptions must be pinned by a green-path assertion** — added as C6, which asserts the schema keys on every passing run. **STATUS UPDATE, later the same day: still UNRESOLVED, and now bounded.** A follow-up pass ran 65 further green gate executions and 3,477 clean doctor samples under load escalated to LA 66 without a single reproduction — see the three entries above, which record what that rules out (co-scheduled CPU/fork pressure as the doctor's perturbation), and which remove two confounders that could each have been mistaken for this flake: a `cp -f` truncation window on `plugins/gmail-commander/scripts/bot.ts`, and a cwd-dependence in the doctor that produced this entry's exact `TOOLKIT_BROKEN` signature on demand. `iter160` and `iter123` remain unexplained.

**2026-09-05**: A unit-correction sweep that fixes the artifacts **and** the generators can still leave a test pinning the old value — and that combination makes reintroducing the bug the path of least resistance. #124/#126 corrected every `hooks.json` timeout from the millisecond spelling to seconds and tightened `scripts/hooks.schema.json`'s `maximum` from 600000 to 600, but `test-posttooluse-subprocess-orphan-cleanup-…iter64-…` still asserted `expected '5000'`. The gate therefore went red **demanding the bug back**, and the quickest way to clear it was to restore an 83-minute timeout on a PostToolUse hook. The assertion was `[[ $timeout == 5000 ]]` — equality against a magic number, which carries no information about what the number _means_ and so cannot distinguish a correction from a regression. Replaced with the corrected value **plus** a bound assertion that the timeout lies within the schema's 1–600 s ceiling, so the four-digit spelling now fails on **meaning** rather than on literal inequality. **Two rules.** (1) A units migration is not complete when the data and the generators are fixed; grep the test corpus for the old literal in the same change, because tests are the one place a corrected value still reads as a defect. (2) Prefer a bound to an equality when the value has a valid range — an equality assertion has to be edited every time the value legitimately changes, and each edit is an opportunity to re-enshrine whatever is currently in the file. Related: the "62 oversized timeouts" figure this work started from was itself unreproducible — the real population was 53, and no counting method yields 62; a survey figure inherited without recount is a premise, not a measurement. **Postscript, same day**: the hook this test guarded was then deleted outright, and the test with it — `posttooluse-subprocess-orphan-cleanup.ts` turned out to have been a no-op for its whole life (its `ps -o cmd=` call is a Linux/procps spelling that macOS `ps` rejects, and it filtered for children of its own pid rather than Claude's), so the timeout being argued over governed a hook that never did anything. A third rule falls out of that: when a test forces you to look closely at a value, check that the thing the value configures actually runs — the gate had been protecting an invariant of dead code.

**2026-09-02**: One named strand of the intermittently-red suite below is now **RESOLVED**: `test-iter117-table-of-contents-auto-injection-…` (red ~2 runs in 11 under the parallel runner, green standalone). The cause was **not** doc drift and **not** the flock scope people assumed — it was `cp`. iter-113 Case 7 and iter-115 Case 5 transiently mutate the shared `docs/marketplace-escape-hatch-marker-reference.md` and restored it with `cp -f backup doc`; **cp opens the destination `O_TRUNC`, so the canonical doc is momentarily ZERO BYTES**. iter-126 had put only iter-117's Case 6 under the shared flock, so its other ~50 grep/awk opens read the doc unlocked and an unlucky one saw the empty file. Measured directly with a tight-loop reader across 6 suite runs: **453 zero-byte observations out of 6,353,768 reads** (~0.7 ms of zero-window per `cp`); after the fix, **0 out of 44,815,049**. Reproduced 3/3 by running iter-117 standalone against a bare `cp -f backup doc` loop — failing in exactly the observed shape, ONE missing TOC entry with every neighbouring assertion green — and the A/B control (same loop using an atomic same-directory `mv`) passed 3/3. Why ~18% and not the ~0.01% an uncorrelated model predicts: `test-iter113/115/117` sort adjacently, so `xargs -P` dispatches them into lanes at nearly the same instant and the reads are strongly correlated with the writers' restore. Fix has two halves — every write to the shared doc now goes through an **atomic same-directory `mv` (rename(2))**, including the real generator's `--write` path, so no reader can ever see a truncated prefix; and every test that READS the shared doc does so under the iter-126 lock, taken as `LOCK_SH` so the three readers do not serialize against each other (`LOCK_EX` stays for the two mutation windows, and a region is always fully closed rather than upgraded in place, since two readers both upgrading would deadlock). This also closed two never-noticed spurious-DRIFT races at iter-113 Case 2 and iter-115 Case 6, both of which ran `--check` outside the lock. 30 post-fix runs: 0 iter-117 failures; suite wall-clock unchanged (16.8–18.0 s vs 17.3 s baseline). **Two meta-lessons.** (1) _An intermittently-red suite is a plural noun._ Everything below is written as if one mechanism explains every red run; it does not, and the search stalled because each new failure was matched against the standing proto-banner hypothesis instead of being captured on its own terms. Loop the suite and tee the actual failing section — the captured red run named its assertion in one line and the mechanism followed in minutes. (2) _A test that reads a shared mutable file must read it under the lock that governs the file_ — protecting only the one read that had already been caught failing leaves every other read exposed. Still open and NOT explained by this: `test-pretooluse-edit-time-orchestrator-iter90…` + `…iter91…` failed together once in those same 30 runs (`subhook count 0 < 7`, a count parsed as 0 from the audit task's output) — a separate flake, unmeasured, do not assume it shares this cause.

**2026-08-30**: Never invoke a proto-shimmed tool bare from a hook command — `bun`, `node`, `moon`, `go` and friends resolve to a `~/.proto/shims/*` shim that re-execs the proto CLI, and proto sniffs `AI_AGENT`/`CLAUDECODE` (both of which Claude Code exports into hook subprocesses), decides it is talking to an agent, and writes `{"type":"message","message":"Detected an AI agent environment, printing as NDJSON…"}` to **stdout** before delegating. The hook's own correct JSON then lands on line 2, so the buffer starts with `{`, Claude Code's single `JSON.parse` throws, and the harness reports `Hook output looks like a JSON object but is not valid JSON` — advice that points at the hook's encoder when every hook already encodes correctly via `JSON.stringify`/`jq`/`json.dumps`. **The noise was not the damage**: exit code stays 0, so this reads as cosmetic, but a hook whose stdout fails to parse has its **decision discarded** — on every polluted call all 15 `PreToolUse:Bash` guards (worktree, uv-enforcement, cwd-deletion, process-storm) silently stopped applying. Measured across 241 tool calls and 8 projects in three days: **2,008 discarded hook decisions**, plus ~3,600 further events that carried the banner but still succeeded (the first pass reported 1,716 polluted events — an undercount, corrected upward); uniform across every bun-invoked hook and **zero** for the two `bash` hooks, which is the fingerprint that indicts the interpreter rather than the hook. Trigger is concurrency — ~15 guards fan out per Bash call and proto's file-lock contention pushes some onto its user-facing path (0/100 polluted at low concurrency, 27–45/100 at 100-way). Fix: prefix every such command with `env -u AI_AGENT -u CLAUDECODE` (42 commands, 9 plugins); **both** vars are required, since `-u AI_AGENT` alone still gave 27/100, and `PROTO_SKIP_USED_AT=1` does nothing. Now enforced by validation #10 in `scripts/validate-plugins.mjs` (`validateHookCommandHygiene`), which also covers bare-path commands whose shebang names a shimmed tool. Two meta-lessons: **(1)** the failure only became visible when Claude Code 2.1.248 added the "looks like a JSON object" check — the fault is older than the message, so a first-observed date is not an introduced-on date; **(2)** when an error names a culprit, verify it — `strings` on the binaries settled in one command (1 hit in `proto`, 0 in all six `bun` binaries) what four independent investigation lenses had split over, and corrected a standing entry in `~/.claude/decisions-failure-modes-CLAUDE.md` that had blamed Bun since 2026-08-16.

**2026-08-05**: `CLAUDE_PLUGIN_ROOT` is not a shell variable — a skill that references it gets an empty string. Claude Code substitutes the exact literal `${CLAUDE_PLUGIN_ROOT}` (braces required) only inside plugin manifests, and injects the var only into hook/MCP subprocess environments; a SKILL.md body is served to the model verbatim. Three corollaries bit us at once: the bare `$…` spelling is unsubstitutable everywhere (including manifests), `${…:-fallback}` never substitutes either (so 51 "guarded" call sites were silently pinned to the L2 marketplace clone, not the installed version), and globbing the version cache for the highest semver picks an orphaned version. Fixed by `scripts/cc-plugin-root`, which reads `installed_plugins.json`; 179 call sites across 20 plugins migrated. Root cause of the authoring mistake was **our own docs teaching the rule inverted** — two reference files claimed it works in skills and not in hooks, which is backwards. [Guard spoke](../plugins/itp-hooks/docs/skill-plugin-root-guard.md)

**2026-08-05**: A guard whose premise has gone stale produces only false positives, and costs more than the bug it once caught. The iter-78 L3-stripped-path guard and its release-time twin (Check 4k) enforced "the L2→L3 cache populator strips everything outside {hooks, skills, commands, agents, plugin.json}". Re-measured: `diff -rq` of the L2 mirror against the live L3 cache returns exactly one difference — the `.in_use` marker Claude Code adds — and `scripts/` is present in the latest cached version of all 27 plugins that ship one. The populator copies the whole tree. Both were retired after the edit-time guard blocked three legitimate edits in a single session, including the one documenting its own retirement. **Lesson: re-verify a guard's premise on a schedule, not just its implementation** — the tests all passed the whole time, because they tested the code against the assumption rather than the assumption against reality. **2026-06-20**: Content-based PostToolUse reminder hooks must call the iter-124 temp-dir helper, same as the lint/type-check subhooks. Two soft-nudge hooks (`posttooluse-pushover-budget-reminder`, `posttooluse-invented-fallback-reminder`) fired on a `Write` to `/tmp/audit17.sh` — a run-once-and-discard script — because they nag on edited file CONTENT but never short-circuited throwaway scratch the way `ty`/`tsgo`/`oxlint`/`biome`/`ssot-principles`/`memory-efficiency` already do via `lib/shared-temporary-directory-…-iter124.ts`. **The orchestrator does NOT centralize this** — each inlined subhook checks the helper individually (verified: iter-93 dispatch runs all subhooks unconditionally via `Promise.all`), so a NEW content-nudge hook silently re-introduces the gap. **Rule**: any PostToolUse hook that injects a reminder based on edited content/path must early-return on `isEditedFilePathInsideTemporaryScratchDirectory…(filePath)` (Write/Edit/MultiEdit) and, for Bash-arm hooks, on `bashCommandWritesThrowawayScriptIntoTemporaryScratchDirectory(command)` — the latter added 2026-06-20 to cover heredoc/redirect/tee/mktemp writes into a temp dir. Two design notes: (1) the Pushover hook's temp-dir skip needed a new `evaluatePushoverHookInput(input)` seam because its pure `detectPushoverMessageConstruction(text)` detector never sees `file_path` — push the input-level skip up a layer rather than threading the path into the text detector; (2) the same audit also exempted test/fixture paths for the Pushover hook (it had been nagging its own fixtures). **2026-03-31**: Terminal text unwrapping for TTS — use `awk`, not FOSS parsers. Spike-tested `par`, `fmt`, `fold`, `pandoc`, `textwrap`, `pysbd` — all fail at joining soft-wrapped continuation lines while preserving bullet boundaries. `par` and `fmt` merge everything into one paragraph (F). `fold` and `pandoc` are passthrough (D). `textwrap` strips indent but doesn't join continuations (D+). `pysbd` splits continuations as separate sentences (D). Only custom `awk` (or equivalent regex) handles the combination of: (1) bullet detection (`·•*-`, numbered, headings), (2) continuation line joining, (3) marker stripping, (4) progressive batching. Zero dependencies, single-pass, built-in on every Unix. Anti-pattern: reaching for Python `textwrap`/`pysbd` or `par` for terminal-copied text — they don't understand bullet-prefixed paragraphs with soft-wrapped continuations.

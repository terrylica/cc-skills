**2026-09-05**: A second strand of the intermittently-red suite is now **NAMED but still UNRESOLVED**, and the reason it stayed anonymous for five weeks was a formatting detail, not a hard problem. The 2026-09-02 entry below prescribes "loop the suite and tee the actual failing section"; that advice was followed and still lost the name, because of how the runner prints. `tasks/test-marketplace-hook-regression-suite` **did** already re-print a failing-file roster at the end — but those lines read `- <path>`, carrying no word any plausible filter would keep, while the three count lines carried `Test files` / `PASSED` / `FAILED`. So a `| grep -E 'PASSED|FAILED'` (or moon's own truncated log skim) kept **exactly the lines without the name and dropped exactly the lines with it**. The roster was there the whole time; it was unsurvivable, which is operationally identical to absent. Fixed with three redundant carriers rather than one: the failing names and exit codes are appended **to the count line itself** (the line empirically proven to survive), every roster line is prefixed with a `FAILED-TEST-FILE` token, and the whole roster is mirrored to **stderr**, which a stdout-only pipe never touches. Deliberately did **not** reuse the existing `FILE-FAIL`/`FILE-PASS` tokens: the iter-75 parity test and the triage task both `grep -c` those, so re-emitting them would have silently inflated two unrelated tallies — a new signal must not be spelled like an existing counted one. With the carriers in, **1 of 10 `moon run repo:check` runs went red and named itself instantly**: `test-iter160-operator-facing-commits-arc-self-diagnosis-…`, failing C3/C4 because the commits-toolkit doctor reported a CRITICAL check failed. Two measurements narrow it without explaining it: D1, a **second** doctor invocation seconds later **in the same run**, saw all CRITICAL checks pass — so the doctor flaps within a single test — and the doctor run standalone at 12-way self-contention was clean 0/24, so it needs full-suite load, not merely concurrency. **Root cause NOT found; no claim is made.** Note this is the same test family the 2026-08-31 entry already named (`iter160`, `iter166`), consistent with its "plural noun" warning. The carriers then earned themselves twice over within the same session: a later unrelated gate run went red on a **different** member, `test-iter123-unified-lookup-cli-auto-detects-query-shape-…` (exit=1), which the count line named immediately and which passed standalone (exit 0) and green on the next full run — a third distinct member caught on its first occurrence rather than after five weeks of anonymity. That is the actual deliverable here: not a fix, but the end of unidentifiable red runs in this suite. One further trap worth generalising: the red log named the FILE but not the CHECK — the same unidentifiable-failure shape one level down, since C3/C4 printed only an aggregate verdict while holding the full JSON in a variable. Emitting the per-check detail immediately exposed that the emitter had been written against **guessed** schema keys (`status`/`detail`; the real ones are `outcome`/`diagnostic_message`), so it would have shipped printing `outcome=None` for every record and been useless at precisely the moment it was needed. **Rule: an error-path emitter is only exercised when something is already broken, so its assumptions must be pinned by a green-path assertion** — added as C6, which asserts the schema keys on every passing run.

**2026-09-05**: A unit-correction sweep that fixes the artifacts **and** the generators can still leave a test pinning the old value — and that combination makes reintroducing the bug the path of least resistance. #124/#126 corrected every `hooks.json` timeout from the millisecond spelling to seconds and tightened `scripts/hooks.schema.json`'s `maximum` from 600000 to 600, but `test-posttooluse-subprocess-orphan-cleanup-…iter64-…` still asserted `expected '5000'`. The gate therefore went red **demanding the bug back**, and the quickest way to clear it was to restore an 83-minute timeout on a PostToolUse hook. The assertion was `[[ $timeout == 5000 ]]` — equality against a magic number, which carries no information about what the number _means_ and so cannot distinguish a correction from a regression. Replaced with the corrected value **plus** a bound assertion that the timeout lies within the schema's 1–600 s ceiling, so the four-digit spelling now fails on **meaning** rather than on literal inequality. **Two rules.** (1) A units migration is not complete when the data and the generators are fixed; grep the test corpus for the old literal in the same change, because tests are the one place a corrected value still reads as a defect. (2) Prefer a bound to an equality when the value has a valid range — an equality assertion has to be edited every time the value legitimately changes, and each edit is an opportunity to re-enshrine whatever is currently in the file. Related: the "62 oversized timeouts" figure this work started from was itself unreproducible — the real population was 53, and no counting method yields 62; a survey figure inherited without recount is a premise, not a measurement. **Postscript, same day**: the hook this test guarded was then deleted outright, and the test with it — `posttooluse-subprocess-orphan-cleanup.ts` turned out to have been a no-op for its whole life (its `ps -o cmd=` call is a Linux/procps spelling that macOS `ps` rejects, and it filtered for children of its own pid rather than Claude's), so the timeout being argued over governed a hook that never did anything. A third rule falls out of that: when a test forces you to look closely at a value, check that the thing the value configures actually runs — the gate had been protecting an invariant of dead code.

**2026-09-02**: One named strand of the intermittently-red suite below is now **RESOLVED**: `test-iter117-table-of-contents-auto-injection-…` (red ~2 runs in 11 under the parallel runner, green standalone). The cause was **not** doc drift and **not** the flock scope people assumed — it was `cp`. iter-113 Case 7 and iter-115 Case 5 transiently mutate the shared `docs/marketplace-escape-hatch-marker-reference.md` and restored it with `cp -f backup doc`; **cp opens the destination `O_TRUNC`, so the canonical doc is momentarily ZERO BYTES**. iter-126 had put only iter-117's Case 6 under the shared flock, so its other ~50 grep/awk opens read the doc unlocked and an unlucky one saw the empty file. Measured directly with a tight-loop reader across 6 suite runs: **453 zero-byte observations out of 6,353,768 reads** (~0.7 ms of zero-window per `cp`); after the fix, **0 out of 44,815,049**. Reproduced 3/3 by running iter-117 standalone against a bare `cp -f backup doc` loop — failing in exactly the observed shape, ONE missing TOC entry with every neighbouring assertion green — and the A/B control (same loop using an atomic same-directory `mv`) passed 3/3. Why ~18% and not the ~0.01% an uncorrelated model predicts: `test-iter113/115/117` sort adjacently, so `xargs -P` dispatches them into lanes at nearly the same instant and the reads are strongly correlated with the writers' restore. Fix has two halves — every write to the shared doc now goes through an **atomic same-directory `mv` (rename(2))**, including the real generator's `--write` path, so no reader can ever see a truncated prefix; and every test that READS the shared doc does so under the iter-126 lock, taken as `LOCK_SH` so the three readers do not serialize against each other (`LOCK_EX` stays for the two mutation windows, and a region is always fully closed rather than upgraded in place, since two readers both upgrading would deadlock). This also closed two never-noticed spurious-DRIFT races at iter-113 Case 2 and iter-115 Case 6, both of which ran `--check` outside the lock. 30 post-fix runs: 0 iter-117 failures; suite wall-clock unchanged (16.8–18.0 s vs 17.3 s baseline). **Two meta-lessons.** (1) _An intermittently-red suite is a plural noun._ Everything below is written as if one mechanism explains every red run; it does not, and the search stalled because each new failure was matched against the standing proto-banner hypothesis instead of being captured on its own terms. Loop the suite and tee the actual failing section — the captured red run named its assertion in one line and the mechanism followed in minutes. (2) _A test that reads a shared mutable file must read it under the lock that governs the file_ — protecting only the one read that had already been caught failing leaves every other read exposed. Still open and NOT explained by this: `test-pretooluse-edit-time-orchestrator-iter90…` + `…iter91…` failed together once in those same 30 runs (`subhook count 0 < 7`, a count parsed as 0 from the audit task's output) — a separate flake, unmeasured, do not assume it shares this cause.

**2026-08-31**: The marketplace hook regression suite is **intermittently red**, and it gates `release-full`. Observed over ~8 runs on 2026-08-31: three failed, each naming a DIFFERENT pair of tests (`1password-context-injection-prejq` + `iter160`, then `path-owner-guard` + `iter119`, then `1password` + `iter166`), and **every one of those tests passes standalone**. One captured failure shows the cause is at least partly the **2026-08-30 proto AI-agent banner below**, surviving in the TEST path: `expected allow, got rc=0 out={"type":"message","message":"Detected an AI agent environment…"}`, and a sibling failure reporting `JSON output routing broken (stdout=1189 bytes, stderr=0 bytes)`. **2026-08-30**: Never invoke a proto-shimmed tool bare from a hook command — `bun`, `node`, `moon`, `go` and friends resolve to a `~/.proto/shims/*` shim that re-execs the proto CLI, and proto sniffs `AI_AGENT`/`CLAUDECODE` (both of which Claude Code exports into hook subprocesses), decides it is talking to an agent, and writes `{"type":"message","message":"Detected an AI agent environment, printing as NDJSON…"}` to **stdout** before delegating. The hook's own correct JSON then lands on line 2, so the buffer starts with `{`, Claude Code's single `JSON.parse` throws, and the harness reports `Hook output looks like a JSON object but is not valid JSON` — advice that points at the hook's encoder when every hook already encodes correctly via `JSON.stringify`/`jq`/`json.dumps`. **The noise was not the damage**: exit code stays 0, so this reads as cosmetic, but a hook whose stdout fails to parse has its **decision discarded** — on every polluted call all 15 `PreToolUse:Bash` guards (worktree, uv-enforcement, cwd-deletion, process-storm) silently stopped applying. Measured across 241 tool calls and 8 projects in three days: **2,008 discarded hook decisions**, plus ~3,600 further events that carried the banner but still succeeded (the first pass reported 1,716 polluted events — an undercount, corrected upward); uniform across every bun-invoked hook and **zero** for the two `bash` hooks, which is the fingerprint that indicts the interpreter rather than the hook. Trigger is concurrency — ~15 guards fan out per Bash call and proto's file-lock contention pushes some onto its user-facing path (0/100 polluted at low concurrency, 27–45/100 at 100-way). Fix: prefix every such command with `env -u AI_AGENT -u CLAUDECODE` (42 commands, 9 plugins); **both** vars are required, since `-u AI_AGENT` alone still gave 27/100, and `PROTO_SKIP_USED_AT=1` does nothing. Now enforced by validation #10 in `scripts/validate-plugins.mjs` (`validateHookCommandHygiene`), which also covers bare-path commands whose shebang names a shimmed tool. Two meta-lessons: **(1)** the failure only became visible when Claude Code 2.1.248 added the "looks like a JSON object" check — the fault is older than the message, so a first-observed date is not an introduced-on date; **(2)** when an error names a culprit, verify it — `strings` on the binaries settled in one command (1 hit in `proto`, 0 in all six `bun` binaries) what four independent investigation lenses had split over, and corrected a standing entry in `~/.claude/decisions-failure-modes-CLAUDE.md` that had blamed Bun since 2026-08-16.

**2026-08-05**: `CLAUDE_PLUGIN_ROOT` is not a shell variable — a skill that references it gets an empty string. Claude Code substitutes the exact literal `${CLAUDE_PLUGIN_ROOT}` (braces required) only inside plugin manifests, and injects the var only into hook/MCP subprocess environments; a SKILL.md body is served to the model verbatim. Three corollaries bit us at once: the bare `$…` spelling is unsubstitutable everywhere (including manifests), `${…:-fallback}` never substitutes either (so 51 "guarded" call sites were silently pinned to the L2 marketplace clone, not the installed version), and globbing the version cache for the highest semver picks an orphaned version. Fixed by `scripts/cc-plugin-root`, which reads `installed_plugins.json`; 179 call sites across 20 plugins migrated. Root cause of the authoring mistake was **our own docs teaching the rule inverted** — two reference files claimed it works in skills and not in hooks, which is backwards. [Guard spoke](../plugins/itp-hooks/docs/skill-plugin-root-guard.md)

**2026-08-05**: A guard whose premise has gone stale produces only false positives, and costs more than the bug it once caught. The iter-78 L3-stripped-path guard and its release-time twin (Check 4k) enforced "the L2→L3 cache populator strips everything outside {hooks, skills, commands, agents, plugin.json}". Re-measured: `diff -rq` of the L2 mirror against the live L3 cache returns exactly one difference — the `.in_use` marker Claude Code adds — and `scripts/` is present in the latest cached version of all 27 plugins that ship one. The populator copies the whole tree. Both were retired after the edit-time guard blocked three legitimate edits in a single session, including the one documenting its own retirement. **Lesson: re-verify a guard's premise on a schedule, not just its implementation** — the tests all passed the whole time, because they tested the code against the assumption rather than the assumption against reality. **2026-06-20**: Content-based PostToolUse reminder hooks must call the iter-124 temp-dir helper, same as the lint/type-check subhooks. Two soft-nudge hooks (`posttooluse-pushover-budget-reminder`, `posttooluse-invented-fallback-reminder`) fired on a `Write` to `/tmp/audit17.sh` — a run-once-and-discard script — because they nag on edited file CONTENT but never short-circuited throwaway scratch the way `ty`/`tsgo`/`oxlint`/`biome`/`ssot-principles`/`memory-efficiency` already do via `lib/shared-temporary-directory-…-iter124.ts`. **The orchestrator does NOT centralize this** — each inlined subhook checks the helper individually (verified: iter-93 dispatch runs all subhooks unconditionally via `Promise.all`), so a NEW content-nudge hook silently re-introduces the gap. **Rule**: any PostToolUse hook that injects a reminder based on edited content/path must early-return on `isEditedFilePathInsideTemporaryScratchDirectory…(filePath)` (Write/Edit/MultiEdit) and, for Bash-arm hooks, on `bashCommandWritesThrowawayScriptIntoTemporaryScratchDirectory(command)` — the latter added 2026-06-20 to cover heredoc/redirect/tee/mktemp writes into a temp dir. Two design notes: (1) the Pushover hook's temp-dir skip needed a new `evaluatePushoverHookInput(input)` seam because its pure `detectPushoverMessageConstruction(text)` detector never sees `file_path` — push the input-level skip up a layer rather than threading the path into the text detector; (2) the same audit also exempted test/fixture paths for the Pushover hook (it had been nagging its own fixtures). Sweep found 3 more filename-scoped hooks (`glossary-sync`, `readme-pypi-links`, `terminology-sync`) missing the guard — added by the harm principle (a throwaway `GLOSSARY.md`/`README.md`/`CLAUDE.md` in `/tmp` is low-probability but free to skip). `code-correctness-guard.sh` already had an inline `case` mirror of the temp-root set. Shipped as a patch release (initial two-hook fix) + a follow-up sweep commit.

**2026-06-11**: A CLAUDE.md over 40k chars is silently load-truncated — its instructions stop being honored, including the very sections being edited. itp-hooks/CLAUDE.md had grown to 112k chars (62% of it two hook TABLES whose Purpose cells accumulated full iter-N migration narratives). Refactor: every section body + the full original tables moved VERBATIM to `plugins/itp-hooks/docs/` spokes (22 files); the hub keeps one-clause table cells + a spoke index (19k chars). **Two traps hit during the move**: (1) verbatim-moved content carries hub-relative links that break one directory deeper (`../../docs/` → `../../../docs/`, `./hooks/lib/` → `../hooks/lib/`, intra-file `#fragments` → spoke paths) — lychee with `--root-dir` catches all of them; (2) a delegated refactor agent created paraphrased spokes and died twice before rewriting the hub — regenerating spokes from the authoritative hub via line-range extraction was both safer and cheaper than trusting agent copies (two were missing content, two linked to spokes that never existed).

**2026-06-11**: Statusline renders native payload echoes ONLY — never composite/inferred state. The ✦ ultracode badge (added 2026-06-10 as `effort==xhigh AND thinking AND NOT fast_mode`) was refuted by live counterexamples within 24 hours: sessions `ea782bfd` (yukon) and `a9861cbf` (claude-sys) rendered xhigh with ultracode OFF, because **effort levels persist across sessions while ultracode is session-only in-memory appState with no statusline-payload field** — so `xhigh ⇏ ultracode`. The 2026-06-10 "zero counterexamples in 34k records" claim sampled a history where xhigh had only ever been reached via ultracode; the persistence leak only manifests in the sessions AFTER an ultracode session ends. **Rule**: a heuristic validated purely on historical co-occurrence is one state-transition away from false-positives — the statusline may only echo fields the payload states directly (the operator interprets `effort:xhigh · thinking:on` themselves). Pinned by two bats tests: render invariant + source-level lint that non-comment `ultracode` mentions in `custom-statusline.sh` equal zero.

**2026-06-10**: Hook file-extension migrations must migrate their test harnesses in the same commit. iter-86 renamed `pretooluse-hoisted-deps-guard.mjs` → `.ts` but the standalone harness kept `node <old>.mjs` — node can't parse TypeScript, so every deny case returned `parsed:null` and 7 tests sat red for 3 weeks while the commit message claimed the harness was updated. **Rule**: after renaming any hook file, grep `*.test.*` for the old basename AND the runner (`node` vs `bun`) before committing. Fixed in `d8a0467c`.

**2026-06-10**: Operator directives that invert behavior must update the executable spec (tests) in the same change. The 2026-04-08 SSH remote-bypass directive (project memory `feedback_ssh_remote_bypass.md`, CRITICAL) made `ssh <remote> 'pip install …'` ALLOW by design, but the 2026-02-28 tests still expected DENY — red for 2 months, and an automated diagnosis initially mis-classified the intentional bypass as a production bug. **2026-06-10**: bats fixtures living INSIDE the parent git repo break hooks that resolve `git rev-parse --show-toplevel` — GIT_ROOT resolves to the cc-skills root, cache files pollute the repo root, and fixture-local assertions never pass (`test_stop_hook.bats` had 4 tests red since inception). **Pattern**: copy the fixture into `$BATS_TEST_TMPDIR`, `git init` + commit it (hooks using `git ls-files --cached` need committed files), so GIT_ROOT == fixture. Fixed in `9c238780`.

**2026-06-10**: Negative-only test assertions are regression-blind. `[[ "$out" != *badge* ]]` passes whether the gating logic is correct OR the whole feature is deleted — adversarially proven by deleting the statusline ultracode block: both "absent" tests stayed green. **Rule**: absence tests must anchor on a positive sibling assertion first (other badges render), then assert absence. Fixed in `c09e6537`.

**2026-06-10**: jq's `//` operator treats `false` (and `null`) as empty — `\(.fast_mode // "")` emits `""` when the flag is legitimately false. Combined with tab-delimited batch decode that is a field-shift bug: tab is IFS _whitespace_, so bash `read` collapses consecutive tabs and every later field shifts left (the statusline's `session_id` received the transcript path). **Pattern**: batch-decode with `` unit separator (non-whitespace, never collapses) + `// false` defaults for booleans. Regression-pinned in `test_statusline.bats` ("x1f batch decode survives false booleans").

**2026-04-07**: Antifragile filesystem side-effects in `claude-tts-companion`. TTS audio silently failed for 50+ minutes because `~/.local/share/tts-debug-wav/` disappeared and `AfplayPlayer.swift` used `try? FileManager.createDirectory(...)` at init time with no per-write recheck. Subtitles rendered (in-memory samples) but `afplay` was never spawned — every request hit `NSPOSIXErrorDomain Code=2` and logged an identical error 25+ times. FileManager.default.createDirectory` anywhere in `claude-tts-companion/Sources/` — grep must return zero. Incident: `.planning/debug/tts-no-audio-260406.md`. Pattern: `.planning/quick/260407-h07-antifragile-fix-for-afplayplayer-wav-wri/` (research, plan, summary, verification). **2026-04-07**: Do NOT replace `afplay` subprocess with `AVAudioPlayer` in `claude-tts-companion`. `AVAudioPlayer`/`AVAudioEngine` was the _previous_ audio implementation and was abandoned because even _initializing_ `AVAudioEngine` in the same process polluted CoreAudio hardware state enough to cause audio jitter under CPU contention (concurrent Swift compilation, MLX/Metal spikes). Subprocess isolation via `posix_spawn(afplay)` keeps the audio path unaffected by in-process GPU/CPU pressure. Git commits `e2e80e1e`, `2be60672`, `c3525c2e`, `815844e2` document the retreat. When a future bug suggests "just use AVAudioPlayer.init(data:) to skip the WAV write", the correct response is to fix the WAV-write side-effect (Antifragile pattern above), not to touch the audio path. Full research: `.planning/quick/260407-h07-antifragile-fix-for-afplayplayer-wav-wri/260407-h07-RESEARCH.md`.

**2026-03-31**: Terminal text unwrapping for TTS — use `awk`, not FOSS parsers. Spike-tested `par`, `fmt`, `fold`, `pandoc`, `textwrap`, `pysbd` — all fail at joining soft-wrapped continuation lines while preserving bullet boundaries. `par` and `fmt` merge everything into one paragraph (F). `fold` and `pandoc` are passthrough (D). `textwrap` strips indent but doesn't join continuations (D+). `pysbd` splits continuations as separate sentences (D). Only custom `awk` (or equivalent regex) handles the combination of: (1) bullet detection (`·•*-`, numbered, headings), (2) continuation line joining, (3) marker stripping, (4) progressive batching. Zero dependencies, single-pass, built-in on every Unix. Anti-pattern: reaching for Python `textwrap`/`pysbd` or `par` for terminal-copied text — they don't understand bullet-prefixed paragraphs with soft-wrapped continuations.

# PII staged-content guard

A pre-commit guard that blocks staged content carrying a forbidden client identifier. This is a **public** repository and client PII has reached it three times; the guard makes the fourth time cost a failed commit instead of a history rewrite.

|           |                                                                          |
| --------- | ------------------------------------------------------------------------ |
| Script    | `scripts/pii-staged-content-guard.ts`                                    |
| Runs from | `.git/hooks/pre-commit`, generated by `scripts/install-hooks.sh`         |
| Test      | `tasks/tests/test-pii-staged-content-guard-*.sh` (`moon run test-hooks`) |
| Denylist  | `~/.local/state/claude-pii-denylist.txt`, override with `$PII_DENYLIST`  |
| Escape    | `PII_GUARD_OK="<reason, ≥12 chars>"`                                     |
| Cost      | ~46 ms on a typical commit                                               |

## What it checks

Every commit, ungated by path. It reads the **staged blob** (`git show :path`), not the working tree, so partially-staged files are judged on the bytes that are actually about to be committed.

It scans **file paths as well as file contents** — one of the three incidents travelled as a surname inside a filename, which a contents-only scan misses.

Matching is case-insensitive, NFC-normalized, Unicode-aware **substring** matching. Each property earns its place: the real leaks were substrings (an email local-part inside a longer address), and a CJK name identifies a person exactly as well as a Latin one, so an ASCII-shaped pattern is not enough.

Binary blobs and deleted paths are skipped. A match exits non-zero and the commit does not proceed.

## Where the denylist lives, and why it is not here

`~/.local/state/claude-pii-denylist.txt`, one term per line, `#` comments and blank lines ignored, mode 600.

**The denylist is deliberately outside any git repository, because a list of forbidden identifiers is itself PII** — committing it would be precisely the leak the guard exists to prevent.

Outside _any_ repo, not merely outside this one. `~/.claude` was considered and rejected: it is a real repo with a real remote, and while a `.gitignore` entry covers it, that entry is one `git add -f`, one ignore-file edit, or one "why is this untracked?" tidy-up away from being wrong — and a file whose only reader is a tool never gets the human glance that would catch it. `~/.local/state` is under no version control at all, which is a property of the location rather than a rule someone has to keep obeying. A backstop ignore rule remains at the old `~/.claude` path in case a denylist is ever recreated there.

Absent or empty, the guard prints `NOT ACTIVE` and passes. The denylist is machine-local, so absence is the normal state on another clone; failing closed there makes the repository uncommittable for everyone without the file, and a guard like that gets deleted rather than configured. The warning is unconditional so the guard is never _quietly_ off.

## What the output says, and what it withholds

The guard reports `file`, `line number`, and a stable `term #N`. It never prints the matched term or the line it sat on.

Hook output is copied far more freely than commits are rewritten — into scrollback, CI logs, screenshots attached to "why is my commit blocked?", and agent transcripts. A guard that echoed the identifier would move the leak from the commit into the log, where nobody goes back to scrub it. One of the three incidents was a document about redaction that reprinted what it redacted; a guard that printed the term would repeat that error in the same repository.

Resolve an ID locally, against a file already on your disk:

```bash
bun scripts/pii-staged-content-guard.ts --explain 3
```

Term IDs index the non-comment, non-blank denylist lines in order, so appending new terms leaves existing IDs stable.

## Exit codes

| Code | Meaning                                                          |
| ---- | ---------------------------------------------------------------- |
| `0`  | Scanned and clean, or bypassed with a reason, or `NOT ACTIVE`    |
| `1`  | A finding — staged content matches the denylist                  |
| `64` | Operator error — unknown argument, or a malformed `--explain` ID |

An unrecognised argument is refused loudly rather than ignored. Exiting 0 on a wrong invocation would look identical to a clean scan, and since this exit code is a gate, that is a bypass leaving no trace and requiring no reason string — the opposite of what the escape hatch below is for. A finding and a mis-invocation get different codes so the second cannot be mistaken for the first.

## Escaping

False positives on a common surname are inevitable, and a guard with no way out gets deleted instead of fixed:

```bash
PII_GUARD_OK="ordinary English word, not the client" git commit -m "..."
```

The reason is required and must run to at least 12 characters. A shorter one is rejected out loud rather than ignored, so nobody walks away believing they bypassed a guard that in fact still blocked them. The reason is echoed into the hook output, which makes the bypass a decision on the record rather than a reflex.

`git commit --no-verify` skips every hook, including this one.

## Requirements and cost

The hook resolves a `bun` interpreter before running the guard, searching `bun` on `PATH`, then `/opt/homebrew/bin/bun`, then `$HOME/.bun/bin/bun`. Non-interactive shells on this machine routinely lack `/opt/homebrew/bin` and have silently broken `bun`, `gh` and `rclone` before, so a bare `bun` is not safe to depend on.

If no interpreter is found the commit is **blocked**, not waved through — an unverifiable commit on a public repo is the case the guard exists for. The message names all three paths searched and states the override, so the failure costs seconds rather than costing the hook. The `PII_GUARD_OK` escape is honored on that path too, under the same ≥12-character reason gate.

Measured on this repo: **~46 ms** for a typical commit (4 files, ~36 KB), ~30 ms for a single small file, ~67 ms for ~1.4 MB staged. About 4 ms of that is Bun process startup. Every commit now pays this, where previously Bun was spawned only when `plugins/` changed.

## Installing

```bash
bash scripts/install-hooks.sh
```

`scripts/install-hooks.sh` is the single source of truth for the generated `.git/hooks/pre-commit`; edit the heredoc there, never the installed hook.

## Follow-up

`scripts/install-hooks.sh` predates the safer git-hook installer convention in `scripts/iter157-*.sh`, which carries a sentinel marker, backs up a pre-existing hook, checks idempotency, and resolves `$GIT_DIR` properly so it works in worktrees. `install-hooks.sh` does none of that and clobbers any existing `pre-commit` unconditionally. Migrating it onto the iter157 pattern is worth doing on its own, and deliberately was not bundled into this security change.
